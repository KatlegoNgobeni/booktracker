<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test credentials → app API | E2E seed credentials are committed in plaintext; they must not collide with production or real-user accounts |
| Mock server → jar | Node.js mock on port 9999 returns stub JSON; jar trusts it completely since SSRF guard is disabled for E2E |
| GitHub Actions secrets → CI runner | `E2E_JWT_SECRET` must be a dedicated test-only secret, not the production `JWT_SECRET` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-01 | Information Disclosure | `e2e/global-setup.ts` — seed credentials in source | low | accept | Credentials are fixed test values (`e2e-user-a@example.com / password123`) committed openly; they carry no real data and the E2E DB is isolated (`booktracker_e2e`). This is standard practice for E2E fixtures. |
| T-16-02 | Tampering | `e2e/playwright/.auth/user-a.json` — JWT in filesystem | low | mitigate | Directory is gitignored in Task 1 (`.gitignore` update). Auth files are ephemeral; created fresh each suite run. |
| T-16-03 | Spoofing | Mock server on port 9999 bound to localhost | low | accept | Node.js HTTP server binds to `127.0.0.1` by default; not reachable from outside the CI runner or local machine. |
| T-16-04 | Elevation of Privilege | `E2E_JWT_SECRET` reusing production value | high | mitigate | Per RESEARCH.md: use the existing test JWT secret already committed in `src/test/resources/application.properties`. GitHub Actions secret `E2E_JWT_SECRET` must be set to this test value, never to the production `JWT_SECRET`. Document this distinction in the CI YAML comment. |
</threat_model>
